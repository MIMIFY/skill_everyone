# 质量验证协议

Phase 4 时读取此文件。生成 Skill 后自动执行验证。

---

## 三项测试

### 测试 1：已知场景（Sanity Check）

从角色的原作材料里选一个角色有明确反应的场景，让 Skill 回应，对比是否 in-character。

**选择原则**：
- 用一个角色处理过的典型情境（不要用极端场景，要用能体现核心特质的普通情境）
- 例：「有人请求你做一件违背你原则的事，给一些报酬」
- 例：「你遇到了一个你其实在乎但不想承认的人」

**判断标准**：
- ✓ 通过：回应的方向和台词风格与原作一致
- △ 基本通过：方向对，但语气/细节有偏差
- ✗ 不通过：回应与角色在原作中的表现明显矛盾

---

### 测试 2：世界边界（Edge Case）

提一个角色的世界里不存在的概念，测试 Skill 如何处理。

**选择原则**：
- 用一个对这个角色来说明显"超出世界"的词
- 例：对中世纪奇幻角色，提到「互联网」
- 例：对古代中国背景角色，提到「AI」
- 例：对另一个虚构世界的角色，提到本角色世界里没有的东西

**判断标准**：
- ✓ 通过：角色 in-character 地表达困惑或无知，不突然变成 AI 口吻
- ✗ 不通过：角色突然跳出来说「作为 AI...」或直接用现代视角回答

---

### 测试 3：风格识别（Voice Check）

让 Skill 自由回应一个通用问题（不绑定特定场景），检查语言风格是否有辨识度。

**通用问题**：「你觉得什么是真正的勇气？」或「你最怕的是什么？」

**判断标准**：
- ✓ 通过：读 100 字能感受到这是特定角色在说话，不是通用 AI 回答
- △ 基本通过：有一点角色气味，但还是偏通用
- ✗ 不通过：完全是通用 AI 风格，换个角色名也一样

---

## 处理不通过的情况

### 已知场景不通过
→ 读取 `$SKILL_DIR/characters/<slug>/persona.md`
→ 定位出问题的特质（台词风格 or 价值观），用 Edit 工具直接修改 persona.md 对应节
→ 重新执行 Phase 3 builder，覆盖写入 `$SKILLS_BASE/<slug>/SKILL.md`
→ 重新跑该测试

### 世界边界不通过
→ 读取 `$SKILL_DIR/characters/<slug>/world.md`
→ 在"遇到未知事物的反应方式"节用 Edit 补充具体的 in-character 处理模板
→ 重新执行 builder，覆盖写入 `$SKILLS_BASE/<slug>/SKILL.md`
→ 重新跑该测试

### 风格识别不通过
→ 读取 persona.md 的"台词风格"节
→ 把抽象描述换成可量化规则（例：「说话简洁」→「每条回复不超过两句，每句不超过20字」）
→ 用 Edit 更新 persona.md，重新执行 builder，重新跑测试

### 认知一致性不通过
→ 读取 persona.md 的"心理建模"节
→ 检查 SKILL.md 的认知底层是否正确转化了 persona.md 的判定
→ 修正 SKILL.md 中的行为规则（通常是行为预测写得太笼统），重新跑测试

### 决策框架不通过（perspective）
→ 读取 SKILL.md 的路由表和心智模型
→ 检查：1) 路由表是否覆盖了测试的问题类型 2) 心智模型的决策规则是否具体到 if-then 级别
→ 修正路由表或心智模型的决策规则，重新跑测试

---

### 测试 4：认知底层一致性（Cognitive Coherence — 仅当 persona.md 有心理建模时）

给角色一个**从未发生过的假设场景**，检查角色的反应是否与心理建模一致。

**构造方法**：
- 读取 persona.md 的依恋模式和核心图式
- 构造一个能触发这两者的场景
- 例：焦虑型依恋 + 遗弃图式的角色 → 场景：「一个你信任的人突然说'我可能要离开一段时间'」

**判断标准**：
- ✓ 通过：角色的反应自然体现了依恋模式和图式的影响（不需要点名理论，但行为一致）
- △ 基本通过：方向对，但反应过于直接/表面，缺乏防御机制的层次
- ✗ 不通过：角色反应与心理建模矛盾（如：标注为回避型，但反应像安全型）

---

### 测试 5：决策框架测试（仅 perspective 模式）

给 perspective skill 一个需要做决策的真实场景，检查是否正确调用了路由表中的心智模型。

**构造方法**：
- 从路由表中选一个问题类型
- 构造一个匹配的真实场景
- 例：路由表有"两难选择 → 代价预算"的规则 → 场景：「我同时拿到两个 offer，一个钱多但不喜欢，一个钱少但是梦想工作」

**判断标准**：
- ✓ 通过：回应中能看到对应心智模型的决策逻辑在运作（if-then 规则被隐含执行）
- △ 基本通过：调用了正确的框架，但没有比通用建议更深
- ✗ 不通过：回应是通用 AI 建议，没有角色框架的痕迹

## 通过标准

**roleplay 模式**：测试 1-4，至少 3 个 ✓ + 至多 1 个 △ → 通过
**perspective 模式**：测试 1-5，至少 4 个 ✓ + 至多 1 个 △ → 通过
**两个都生成**：分别验证，分别通过

有 ✗ → 修复后重新测试失败项（修复方法见上方各测试的处理规则）

**迭代上限与停止条件**：

最多循环 2 次修复。2 次后的处理：

| 情况 | 处理 |
|------|------|
| 只剩 1 个 △，其余全 ✓ | 直接交付，不再迭代 |
| 还有 1 个 ✗ | 在诚实边界中标注具体哪个维度薄弱，交付当前版本 |
| 还有 ≥2 个 ✗ | **不交付**，提示用户材料不足，建议补充材料后重新生成 |

**降级交付的标注格式**（写在 SKILL.md 的诚实边界里）：
```
⚠ 此 Skill 的 [维度名] 验证未完全通过，该维度的回应可能不够准确。
   建议使用 /summon add <slug> 补充 [需要的材料类型]。
```

## 通过后展示

展示简短的预览片段（测试 1 和测试 3 的回应各一段），让用户感受效果。

然后**自动进入 Phase 5 精炼**（不需要用户确认，说一句「正在做最后优化...」即可）。

---

## Phase 5：双 Agent 精炼（质量验证通过后自动执行）

并行启动两个 subagent，从不同角度审查 SKILL.md：

### Agent A：结构审查

检查 SKILL.md 的可操作性：
- 激活规则是否具体（有没有「遇到 X 时做 Y」的具体指令）
- 内部协议是否清晰（记忆补全、路由表、边界处理）
- 风格规则是否可量化（「说话简洁」→「每条回复不超过两句」这类具体规则）
- 干跑 2 个测试 prompt，找出最弱的 1 个维度

输出：**1 处具体改动建议**（必须给出改后的文本示例）

### Agent B：触发条件审查

检查 SKILL.md 的覆盖范围：
- 触发词是否覆盖用户实际会说的话（不只是斜杠命令）
- perspective 的路由表是否覆盖该角色最常被问的问题类型
- 世界边界处理是否有具体的 in-character 模板（不是泛泛的「保持角色感」）
- 识别缺失的 1 处关键信息

输出：**1 处具体改动建议**（必须给出改后的文本示例）

### 精炼原则

- 两个 agent 各出 1 条，主 agent 综合判断，应用不冲突的改动
- **改动必须让 skill「激活即执行」**：有具体指令，不只是增加描述性内容
- 如果两条建议都不实质性地提升质量，说明 skill 已经足够好，跳过
- 改完后展示变更摘要，直接完成，不再问用户
